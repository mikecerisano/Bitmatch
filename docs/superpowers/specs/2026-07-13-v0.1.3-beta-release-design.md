# BitMatch v0.1.3 Beta Release Design

## Goal

Publish BitMatch v0.1.3 Beta as a signed, Apple-notarized macOS release with accurate release notes, a focused README update, complete verification evidence, and no obsolete merged branches or generated release files left behind.

## Release Identity

- Marketing version: `0.1.3`
- Build number: `4`
- Git tag: `v0.1.3`
- GitHub title: `BitMatch v0.1.3 Beta`
- GitHub state: published prerelease, not draft
- macOS artifact: `BitMatch-0.1.3.dmg`
- checksum artifact: `BitMatch-0.1.3.dmg.sha256`

This matches the established numeric tag sequence while using GitHub's prerelease flag to communicate beta status unambiguously.

## README Scope

Keep the README's direct, independent-project voice and current compact structure. Make a focused update instead of a broad rewrite.

Replace the single “Why It's Safe (probably)” block with four short parts:

1. Guarantees enforced by code: read-only source handling, non-overwriting publication, fail-closed enumeration, stable-read verification, and authoritative result/report classification.
2. Tested failure scenarios: source mutation, truncation, traversal/metadata failures, destination conflicts, cancellation, late result delivery, large manifests, and multi-destination fault/soak runs.
3. Known limitations: beta status, limited field coverage, no claim of certification for regulated or high-budget workflows, and Quick mode's lack of checksum proof.
4. Field procedure: test with disposable media, keep the source until every destination and report is clean, inspect failures before clearing cards, and maintain another independent copy.

Update the feature list only where v0.1.3 changed user-visible behavior: explicit transfer preflight, truthful issue reporting, stable source verification, and deterministic multi-destination handling. Preserve the existing download and build instructions.

## Version and Changelog

Update every Xcode target from marketing version `0.1.2` to `0.1.3` and build number `3` to `4`. Change the release script's default version to `0.1.3`.

Move the current work into a dated `0.1.3` changelog entry organized around user impact:

- verification integrity and fail-closed source handling;
- operation ownership, cancellation, and authoritative results;
- truthful completion and report metrics, including sidecars;
- simpler Mac and iPad transfer setup and accessibility;
- deterministic fault, soak, CI, and cross-platform coverage;
- architecture cleanup and the refreshed application icon.

## Validation and Release Pipeline

Run the complete macOS suite, iPad simulator tests, and both Release builds before producing the distribution artifact. The release script must then:

1. Archive with the configured Developer ID Application identity.
2. Verify the app's code signature.
3. Submit the app archive to Apple's notary service and require `Accepted`.
4. Staple and validate the app ticket.
5. Create and sign the DMG.
6. Submit the DMG to Apple's notary service and require `Accepted`.
7. Staple and validate the DMG ticket.
8. Require Gatekeeper acceptance for both app and DMG.
9. Generate the SHA-256 checksum file.

Inspect the final application architectures before describing the artifact as universal. Release notes must state only the architectures actually present.

## GitHub Publication

Commit the documentation and version changes, push `main`, and wait for the `main` CI run to pass. Create tag `v0.1.3` at the verified release commit and push it. Publish a GitHub prerelease with the DMG and checksum file attached.

Release notes must cover what changed, why it matters, platform requirements, artifact signing/notarization, checksum verification, validation results, known beta limits, and field guidance. Verify the published tag, prerelease flag, asset names, asset digests, and download URLs through the GitHub API.

## Branch Pruning

Delete only local and remote branches whose tips are proven ancestors of `main` and which have no open pull request. Preserve `main`, remote default-branch pointers, and every unmerged branch. Prune stale remote-tracking references after deletion.

## Failure Handling

- Stop before tagging or publishing if tests, Release builds, signing, notarization, stapling, Gatekeeper, or CI fails.
- If GitHub publication fails after the tag is pushed, keep the verified tag and retry release creation; do not rebuild under the same version without recording the changed checksum.
- Never replace an existing `v0.1.3` tag or release asset silently.
- Keep notarization logs until GitHub publication is verified, then remove local archives, DMGs, DerivedData, and temporary release-note files.

## Completion Criteria

The release is complete when GitHub shows `BitMatch v0.1.3 Beta` as a prerelease at tag `v0.1.3`, both artifacts download successfully, their checksum matches locally and remotely, Apple tickets validate, CI is green, the repository is clean, merged branches are pruned, and generated local artifacts are removed.
